plim-ui treats accessibility as a baseline requirement. Components use semantic HTML first, keyboard support by default, and ARIA only when native semantics are not enough.

01

Semantic structure

Use the correct HTML elements for landmarks, headings, buttons, and links.

 02

Keyboard and focus

All interactive components must be operable by keyboard with visible focus.

 03

ARIA with restraint

Add ARIA only when it improves assistive technology behaviour.

In practice

  • Buttons use native <button> semantics via plimButton.
  • Landmarks such as <header> and <aside> are used internally.
  • Focus rings use --plim-focus-ring-* tokens for consistent visibility.
  • Each component docs page includes accessibility notes for that primitive.

Motion

Transitions use --plim-duration-* and --plim-ease-default. Components respect prefers-reduced-motion: reduce by disabling non-essential animation — for example spinner rotation, sidebar slide transitions, and toggle control scale effects.

When adding motion, keep it functional (open/close feedback, loading state) rather than ornamental. If meaning depends on animation, provide a static alternative.

High contrast

Interactive states include @media (forced-colors: active) rules where colour carries meaning — for example primary buttons, badges, tabs, sliders, and option list highlight/selected states. Prefer system colours such as Highlight, HighlightText, and ButtonBorder rather than hard-coded palette values.

Never rely on colour alone for status or selection. Pair semantic colours with text, icons, weight, or borders.

Disabled and muted content

Disabled controls use --plim-opacity-disabled. Subtle or de-emphasized UI can use --plim-opacity-muted. Prefer these tokens over scattered opacity literals so contrast stays predictable in both themes.
